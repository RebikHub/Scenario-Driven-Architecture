## Что такое SDA

Scenario-Driven Architecture (SDA) — это подход к организации кода, при котором:

- **Первичен сценарий** — пользовательский путь от первого шага до последнего
- **Файловая структура = карта приложения** — роут = домен, саброут = сабдомен, шаг → подшаг
- **Всё локально по умолчанию** — код живёт там, где используется
- **Общее — только по доказанной необходимости** — абстракции растут снизу вверх
- **Слои опциональны и локальны** — `ui`, `model`, `api` внутри роута, а не глобально
- **Независимость разработчиков** — каждый домен-роут-модуль изолирован. Разные разработчики могут работать параллельно над разными доменами, не пересекаясь и не мешая друг другу

SDA не предписывает жёсткую структуру папок. Он задаёт принципы, которые помогают принимать согласованные решения о том, где должен жить код. **Роутинг — основа всего:** роут = домен, саброут = сабдомен. Подход не привязан к конкретному фреймворку и работает с React, Vue, Angular, Next.js, Nuxt и другими.

## Предпосылки

SDA не появился из вакуума. Крупные фреймворки и сообщества независимо пришли к похожим решениям:

| Фреймворк | Механизм | Сходство с SDA |
|-----------|----------|----------------|
| **Next.js App Router** | Папка = роут, layout = контекст, page.tsx = шаг | Полное совпадение философии |
| **React Router v7 (Remix)** | Плоские роуты + layout-файлы для контекста | Layout как граница, роуты как шаги |
| **Nuxt Pages + Layers** | Папка = роут, Layers = изолированные домены | Домен как набор страниц в папке |
| **Angular Standalone** | Роуты как оркестратор, компоненты с зависимостями | Роутинг как карта сценария |

Индустрия движется к **Route-as-Context Architecture** — где вложенность папок = вложенность URL = вложенность контекста. SDA — это методология над этим трендом: **правила того, что класть внутрь роута и когда выносить наружу**.

## Пять принципов

### Принцип 1: Контекст первичен

> Компонент, его конвертеры, константы, хуки и типы живут вместе — в папке того сценария, к которому они относятся. Файловая структура отражает принадлежность к бизнес-процессу, а не технический тип файла.

**Роутинг — основа контекста.** Роут определяет домен, саброут — сабдомен. Layout вторичен: сабдомены внутри одного родительского домена могут иметь разные лейауты, разную визуальную составляющую. Граница домена определяется положением в дереве роутинга и дизайном приложения, а не общим шаблоном страницы.

**Пример:**
```
statement/income/
├── StatementIncome.tsx       # UI шага «Доходы»
├── useIncome.ts              # Логика шага
├── convertorsIncome.ts       # Конвертеры (локальные)
├── constants.ts              # Константы шага
└── types.ts                  # Типы шага
```

Код сгруппирован по сценарию, а не по типу файла — потому что меняется по одной причине (изменился шаг «Доходы»).

### Принцип 2: Общее — по требованию, а не по предположению

> Код выносится на глобальный уровень (`app/services`, `app/components`) только когда минимум два разных домена нуждаются в идентичном контракте. Дублирование на ранних этапах безопаснее, чем неправильная абстракция.

**Правило трёх:**
- Первый раз — кладём локально
- Второй раз — всё ещё локально, даже если код похож
- Третий раз — выносим, если контракт действительно идентичен

**Почему не сразу в shared:**
- Похожий код ≠ одинаковый код
- Сегодня похожи — завтра разойдутся из-за разных требований
- Преждевременная абстракция создаёт жёсткую связность, которую дорого разрывать

### Принцип 3: Layout как опциональная граница контекста

> Layout (лейаут) может хранить данные и состояние, которые валидны только в рамках текущего домена/роута, но **не является обязательным**. Границу домена определяет роутинг, а не layout. Сабдомены могут иметь разные лейауты или не иметь их вовсе.

**Примеры границ контекста:**
```
StatementLayout → ID заявления, текущий шаг, флаг редактирования
OrderLayout     → ID заказа, текущий шаг, выбранные опции
ProfileLayout   → Раздел профиля, данные пользователя
AuthLayout      → Токен, статус аутентификации
```

Эти лейауты не пересекаются. Данные одного домена не просачиваются в другой через глобальный стор.

### Принцип 4: Сценарий как first-class citizen

> Роуты описывают не просто навигацию, а бизнес-процесс с ветвлениями, условиями и последовательностью шагов. Файл роутов — это карта сценария, читаемая как документация.

**Пример — сценарий «Заказ услуги»:**
```typescript
// OrderRoutes.tsx — оркестратор сценария
<Route path="order" element={<OrderLayout />}>
  <Route path="condition" element={<OrderCondition />} />      // Шаг 1: Условия
  <Route path="containers" element={<OrderContainers />} />    // Шаг 2: Контейнеры
  <Route path="recipients" element={<OrderRecipients />} />    // Шаг 3: Получатели
  <Route path="notification" element={<OrderNotification />} />// Шаг 4: Уведомления
  <Route path="confirm" element={<OrderConfirm />} />          // Шаг 5: Подтверждение
</Route>
```

Новый разработчик открывает этот файл и сразу видит пользовательский путь. Ему не нужно собирать пазл из `features/order-condition`, `features/order-containers`, `entities/container`.

### Принцип 5: Стор персонифицирован

> Глобальное состояние разделено по доменам. Стор заявления не содержит данные реестров. Стор заказа не содержит данные профиля. Кросс-доменные данные (пользователь, токен, язык) — отдельный сервис.

**Пример:**
```
store/
├── user.ts         # Данные пользователя (кросс-доменный сервис)
├── order.ts        # Только процесс заказа
├── statement.ts    # Только процесс заявления
├── toast.ts        # Уведомления (кросс-доменный сервис)
└── localization.ts # Язык интерфейса
```

Если в заявлении нужно добавить флаг «черновик» — он попадает в `statement.ts` и не затрагивает заказы. Если в заказе меняется логика шагов — `order.ts` и только он.

## Терминология

| Термин SDA | Определение | Аналог в DDD |
|------------|-------------|--------------|
| **Домен** | Раздел приложения, выделенный по дизайну и роутингу. Имеет корневой роут и может содержать сабдомены. Layout не обязателен — границу определяет положение в дереве роутинга | Bounded Context |
| **Роут** | Контейнер сценария, основа архитектуры. Роут = домен, саброут = сабдомен. Определяет границы контекста данных и положение в дереве навигации | Aggregate Root |
| **Сценарий** | Полный бизнес-процесс от первого до последнего шага с ветвлениями | Process Manager / Saga |
| **Шаг** | Один экран/состояние внутри сценария со своим контрактом данных | Application Service |
| **Лейаут** | Опциональный контекст данных и состояния, живущий пока живёт домен/роут. Сабдомены могут иметь собственный layout или наследовать родительский | Session State |
| **Сервис** | Инфраструктурный слой (`app/services/`): API-запросы, утилиты, провайдеры. Может содержать полное описание запросов к серверу, отдельно от доменов-роутов | Shared Kernel (отложенный) |
| **UI-кит** | Переиспользуемые визуальные примитивы без бизнес-логики | Component Library |
| **Стор** | Персонифицированное хранилище состояния конкретного домена | Aggregate Store |

## Базовая файловая структура

```
src/
├── app/                          # Глобальный уровень приложения
│   ├── api/                      # Инфраструктурный слой API
│   │   ├── baseApi.ts            # Базовый экземпляр axios/fetch
│   │   ├── endpoints/            # Эндпоинты, сгруппированные по доменам (полное описание запросов к серверу)
│   │   └── hooks/                # Обёртки useQuery / useMutation
│   ├── components/               # Глобальные компоненты
│   │   └── ui-kit/               # UI-кит: кнопки, инпуты, модалки, таблицы
│   ├── services/                 # Инфраструктурный слой (API, утилиты, провайдеры)
│   │   ├── hooks/                # useScreenWidth, useLocalization, useKeyDown
│   │   ├── utils/                # converterDate, storage, validators
│   │   └── providers/            # Провайдеры контекста (темы, локали)
│   ├── store/                    # Персонифицированные сторы
│   │   ├── user.ts               # Данные пользователя
│   │   ├── order.ts              # Состояние заказа
│   │   ├── statement.ts          # Состояние заявления
│   │   └── toast.ts              # Уведомления
│   ├── router/                   # Оркестраторы сценариев
│   │   ├── RootRoutes.tsx        # Корневой роутер
│   │   ├── main/
│   │   │   ├── MainRoutes.tsx    # Вход в домен main
│   │   │   ├── order/OrderRoutes.tsx
│   │   │   └── profile/ProfileRoutes.tsx
│   │   └── auth/AuthRoutes.tsx
│   ├── styles/                   # Глобальные стили, переменные, миксины
│   └── types/                    # Общие типы и енамы
│
├── pages/                        # Страницы — точки входа в домены
│   ├── main/
│   │   ├── layout/MainLayout.tsx # Лейаут домена main
│   │   ├── order/                # Домен «Заказ»
│   │   │   ├── layout/OrderLayout.tsx
│   │   │   ├── condition/        # Шаг 1
│   │   │   ├── containers/       # Шаг 2
│   │   │   ├── recipients/       # Шаг 3
│   │   │   ├── notification/     # Шаг 4
│   │   │   └── confirm/          # Шаг 5
│   │   ├── profile/              # Домен «Профиль»
│   │   │   ├── layout/ProfileLayout.tsx
│   │   │   ├── account/
│   │   │   ├── orders/
│   │   │   ├── recipients/
│   │   │   └── tariff/
│   │   └── components/           # Общие компоненты домена main
│   │       ├── container/
│   │       ├── feedback/
│   │       └── recipient/
│   └── auth/                     # Домен «Аутентификация»
│       ├── layout/AuthLayout.tsx
│       ├── login/
│       ├── signup/
│       └── reset-password/
│
└── assets/                       # Статические ресурсы
    ├── fonts/
    └── images/
```

**Ключевые точки:**
- `pages/` содержит только точки входа — лейауты и страницы
- Домен может иметь свой лейаут, но это не обязательно. Layout вторичен — границу домена определяет положение в дереве роутинга
- Шаги сценария лежат внутри домена
- Общие компоненты/формы нескольких сабдоменов одного домена — в `pages/[domain]/components/` или `pages/[domain]/shared/`
- Общие компоненты для разных доменов — в `app/components/` (UI) или `app/services/` (бизнес-логика/инфраструктура)
- Глобальные абстракции — только в `app/`

## Локальные слои внутри роута

SDA не запрещает использовать слоистую структуру. Напротив — для сложных шагов это рекомендуется. Разница в том, что слои в SDA **локальны и опциональны**, а не глобальны и обязательны.

### Когда использовать слои

```
statement/income/
├── ui/                          # Слой представления
│   ├── StatementIncome.tsx
│   └── IncomeTable.tsx
├── model/                       # Слой логики и состояния
│   ├── useIncome.ts
│   └── incomeReducer.ts
├── api/                         # Слой запросов
│   └── incomeEndpoints.ts
├── utils/                       # Слой утилит
│   └── convertorsIncome.ts
├── constants/                   # Слой констант
│   └── constants.ts
└── types/                       # Слой типов
    └── types.ts
```

### Когда слои не нужны

```
profile/account/
└── ProfileAccount.tsx           # Простая страница — один файл
```

### Когда оправданы локальные слои

| Критерий | Глобальные слои | Локальные слои (SDA) |
|----------|-----------------|---------------------|
| **Где определены** | На уровне всего приложения | Внутри роута, опционально |
| **Кто решает** | Архитектор единожды для всех | Разработчик для каждого роута |
| **Если слой не нужен** | Всё равно создавай | Не создавай — значит роут простой |
| **Связанность** | Код сценария в 5 глобальных слоях | Код сценария в одной папке |
| **Рефакторинг** | Перенос между слоями — боль команды | Переименовал папку — никто не заметил |

## Правила принятия решений

### Где разместить новый код?

```
Новый компонент / хук / утилита
│
├─ Используется только в одном шаге сценария?
│  └─ Положи в папку этого шага
│
├─ Используется в нескольких шагах одного домена?
│  └─ Положи в pages/[domain]/components/ или pages/[domain]/shared/
│
├─ Используется в нескольких доменах?
│  ├─ Имеет бизнес-логику?
│  │  └─ Положи в app/services/
│  └─ Чистый UI без бизнес-логики?
│     └─ Положи в app/components/ui-kit/
│
└─ Это состояние домена?
   └─ Положи в app/store/[domain].ts
```

### Когда выносить в `app/services`?

`app/services/` — это **инфраструктурный слой**. Сюда попадает код, который обеспечивает работу приложения на системном уровне, а не принадлежит конкретному бизнес-процессу:

- **API-запросы** — полное описание запросов к серверу (эндпоинты, типы ответов, базовые конвертеры)
- **Утилиты** — работа с датами, storage, валидаторы
- **Провайдеры** — тема, локализация, контекст приложения

Внутри роута-домена может быть **локальная реализация запроса** с индивидуальной обвязкой, касающейся конкретного домена (специфические конвертеры, мапперы ответа под UI, дополнительная валидация). Это **не дублирование** — это разный уровень ответственности: инфраструктурный (app) vs прикладной (домен).

**Условия для выноса в `app/services/`:**
1. Код используется **как минимум в двух разных доменах**
2. Контракт (входные и выходные данные) **идентичен** в обоих случаях

Если контракты разные — оставляем локально, даже если код выглядит похоже. **Внешнее сходство не равно семантическому единству.**

### Когда создавать новый домен?

Граница домена определяется **дизайном приложения** и возможностью изолировать модуль со всеми вложенными подразделами и саброутами.

Новый домен создаётся, когда:
- В дизайне выделяется самостоятельный раздел, который можно изолировать в отдельный модуль
- Раздел имеет собственный роутинг (корневой путь, от которого строятся саброуты)
- Над разделом может работать отдельный разработчик/команда, не пересекаясь с другими доменами
- Данные и состояние процесса не пересекаются с существующими доменами

**Роутинг — основа всего.**
Домен — это роут. Сабдомен — это саброут.
Layout и визуальная составляющая вторичны: сабдомены могут иметь разные лейауты, разную стилистику. Главное — их положение в дереве роутинга.

### Когда разбивать домен на сабдомены?

Сабдомен создаётся, когда внутри домена появляется группа шагов, которую можно выделить в отдельный подраздел со своим саброутом.

Сабдомен **не обязан** иметь собственный layout — он наследует layout родительского домена или использует другой. Layout не определяет границу сабдомена. Границу определяет положение в дереве роутинга.

Пример: в заявлении шаги «Члены семьи» образуют сабдомен: `statement/family-members/search` → `create` → `documents` → `employment` → `property`. У них может быть свой layout, а может и не быть — это не влияет на то, что `family-members` — сабдомен.

### Коммуникация между доменами

В идеале **коммуникации между доменами быть не должно**. Каждый домен — это отдельный роут. При переходе на новый маршрут общий компонент или лейаут получает базовые данные с сервера заново. Домены не импортируют компоненты друг друга и не читают стор чужого домена.

На практике возможны исключения:
- **Кросс-доменные данные** (пользователь, токен, язык) — хранятся в `app/store/` или `app/services/` и доступны всем доменам
- **Локальное хранение** — если два домена (например, `profile` и `order`) используют общие данные, они могут получать их из одного источника (localStorage, единый сторадж), но это деталь реализации конкретного приложения

Применение кросс-доменного взаимодействия зависит от архитектуры конкретного приложения и не регламентируется методологией. Общий принцип: если данные можно получить с сервера при переходе на роут — получайте с сервера.

## Масштабирование: от простого к сложному

SDA масштабируется без смены парадигмы. Одна и та же логика работает для любого размера приложения: **роутинг определяет структуру, вложенность роутов = вложенность доменов**. Layout и визуальная составляющая вторичны и могут меняться внутри домена.

### Уровень 1: Простая страница

```
pages/admin/users/
└── Users.tsx                   # Один файл — одна страница
```

### Уровень 2: Страница с подразделами

```
pages/admin/users/
├── UsersList.tsx               # Список пользователей
├── UsersCreate.tsx             # Создание
```

## SDA и современные фреймворки

SDA не конфликтует с фреймворками, а **усиливает** их. Вы можете реализовать SDA в любом фреймворке:

### Next.js App Router

```
app/
├── layout.tsx                  # Корневой layout
├── (main)/                     # Группа роутов (домен main)
│   ├── layout.tsx              # MainLayout
│   ├── order/
│   │   ├── layout.tsx          # OrderLayout
│   │   ├── condition/page.tsx  # Шаг 1
│   │   ├── containers/page.tsx # Шаг 2
│   │   └── confirm/page.tsx    # Шаг 3
│   └── profile/
│       ├── layout.tsx          # ProfileLayout
│       └── page.tsx
└── (auth)/
    ├── layout.tsx              # AuthLayout
    ├── login/page.tsx
    └── signup/page.tsx
```

Next.js даёт файловую систему как роутер, SDA даёт правила: что класть в роут, когда выносить в `app/services/`.

### React Router v7

```typescript
// routes/main/order/OrderRoutes.tsx
<Route path="order" element={<OrderLayout />}>
  <Route path="condition" element={<OrderCondition />} />
  <Route path="containers" element={<OrderContainers />} />
  <Route path="confirm" element={<OrderConfirm />} />
</Route>
```

### Angular Standalone

```typescript
export const ORDER_ROUTES: Routes = [
  {
    path: 'order',
    component: OrderLayoutComponent,
    children: [
      { path: 'condition', component: OrderConditionComponent },
      { path: 'containers', component: OrderContainersComponent },
      { path: 'confirm', component: OrderConfirmComponent },
    ]
  }
];
```

Фреймворк даёт механизм роутинга. SDA даёт методологию: как организовать код внутри этих роутов и как делить домены.

## Примеры из реальных проектов

### Пример 1: Сложный многошаговый сценарий 

```
statement/                                  # Домен «Заявления»
├── StatementLayout.tsx                     # ID заявления, текущий шаг
├── statement-client-search/                # Шаг 1: Поиск клиента
├── statement-client-create/                # Шаг 1а: Создание клиента (ветвление)
├── statement-program/                      # Шаг 2: Выбор программы
├── statement-family-members/               # Шаг 3: Члены семьи (сабдомен)
│   ├── StatementFamilyCreate.tsx
│   ├── StatementFamilyEdit.tsx
│   ├── StatementFamilyDocuments.tsx
│   ├── StatementFamilyEmployment.tsx
│   └── StatementFamilyProperty.tsx
├── statement-income/                       # Шаг 4: Доходы
│   ├── StatementIncome.tsx
│   ├── hooks/useIncome.ts
│   └── utils/convertorsIncome.ts
├── statement-property/                     # Шаг 5: Имущество
├── statement-employment/                   # Шаг 6: Занятость
└── statement-contract-conclusion/          # Шаг 7: Заключение договора
    ├── StatementContractConclusionWithEditing.tsx    # Ветвление
    └── StatementContractConclusionWithoutEditing.tsx

store/statement.ts                          # Только процесс заявления
```

**Особенности:**
- 40+ шагов сценария сгруппированы в домене `statement`
- Сабдомен `family-members` содержит собственный мини-сценарий
- Ветвления (`WithEditing`/`WithoutEditing`) — прямо в именах файлов
- Конвертеры `convertorsIncome.ts` живут в шаге «Доходы», а не в `shared`
- Стор `statement.ts` хранит только состояние процесса заявления

### Пример 2: Личный кабинет с заказом услуги 

```
main/
├── MainLayout.tsx                           # Лейаут ЛК
├── order/                                   # Домен «Заказ»
│   ├── OrderLayout.tsx                      # ID заказа, текущий шаг
│   ├── condition/OrderCondition.tsx         # Шаг 1: Условия
│   ├── containers/OrderContainers.tsx       # Шаг 2: Контейнеры
│   ├── recipients/OrderRecipients.tsx       # Шаг 3: Получатели
│   ├── notification/OrderNotification.tsx   # Шаг 4: Уведомления
│   └── confirm/OrderConfirm.tsx             # Шаг 5: Подтверждение
├── profile/                                 # Домен «Профиль»
│   ├── ProfileLayout.tsx
│   ├── account/ProfileAccount.tsx
│   ├── orders/ProfileOrders.tsx
│   ├── recipients/ProfileRecipients.tsx
│   └── tariff/ProfileTariff.tsx

    ├── feedback/Feedback.tsx

store/
├── user.ts                                  # Данные пользователя
├── order.ts                                 # Только процесс заказа
```

**Особенности:**
- Два независимых домена: `order` и `profile`

> SDA не описывает как реализовать — она описывает как думать. Конкретная реализация (именование, тестирование, API, кэширование) зависит от приложения и определяется командой.

SDA — это принципы вместо правил, свобода вместо ограничений, простота вместо формальности. Она решает главную проблему фронтенд-проектов - где должен жить код. Ответ — там, где он используется в папке роута-домена.
